## Detail — Apa yang Sudah Jadi

**Fase 0 & 1** — lihat riwayat sebelumnya (Node.js portable, Next.js 16 + Tailwind v4 scaffold, Prisma schema, shell navigasi). Tambahan sesi ini:
- Komponen UI reusable di `src/components/ui/`: `Button` (variant default/outline/solid/danger/ghost), `Badge` (+ helper `statusSiagaColor`/`statusMisiColor`/`urgensiColor`/`statusSertifikasiColor` — badge status FRD §10.8 selalu ada label teks, bukan cuma warna), `Card`/`CardHeader`/`CardTitle`/`CardContent`, `Input`/`Textarea`/`Select`/`Label`, `Chip`
- `Drawer` (slide dari kanan, untuk profil CV anggota / detail Misi nanti) & `Modal` (untuk form Buat Misi nanti) — keduanya Radix Dialog based, animasi didefinisikan di `globals.css` (`overlay-show`, `modal-show`, `drawer-slide-in`)
- **Next.js 16 migration**: `middleware.ts` di-rename ke `src/proxy.ts` (Next 16 mendeprecate nama "middleware", lihat `node_modules/next/dist/docs/.../proxy.md`) — build sekarang bersih tanpa warning deprecation

**Fase 2 — Auth & RBAC (selesai, diverifikasi end-to-end):**
- `src/lib/auth.ts` — Auth.js v5, Credentials provider, password di-hash bcrypt, session JWT dengan `role` & `anggotaId` di token (lihat `src/types/next-auth.d.ts` untuk type augmentation — **catatan penting**: augmentasi `JWT` harus target modul `@auth/core/jwt`, BUKAN `next-auth/jwt` yang cuma re-export dan tidak ke-merge oleh TypeScript)
- `src/app/login/` — halaman login (Server Action `loginAction` via `useActionState`, bukan client-side `signIn` dari `next-auth/react`) + `src/lib/auth-actions.ts` (`signOutAction`)
- `src/proxy.ts` — RBAC: belum login → redirect `/login`; role `ANGGOTA` terkunci ke `/m/*`; role lain (Super Admin/Operator/Analis) terkunci ke Command Center; sudah login tapi buka `/login` → redirect otomatis ke area masing-masing
- Topbar & Sidebar sekarang menerima `user` (session asli) dari `(command)/layout.tsx` (server component, panggil `auth()`) — nama, role label, dan tombol Keluar semua nyata, bukan dekoratif lagi
- **Diverifikasi manual via curl** (bukan cuma asumsi): login benar → cookie session ter-set & `/overview` menampilkan nama+role asli; password salah → redirect `?error=CredentialsSignin`; role ANGGOTA ke `/overview` → auto-redirect ke `/m`; role lain ke `/m` → auto-redirect ke `/overview`; sign-out → cookie ter-clear, `/overview` kembali redirect ke `/login`

**Fase 3 (sebagian) — Seed data:**

**Fase 5 — Manajemen Data Anggota (selesai, RBAC server-side + CRUD teruji end-to-end):**
- `src/lib/anggota-data.ts` — `getAnggotaFullList()` memuat seluruh detail (profil, lokasi, sertifikasi, pelatihan, penugasan) sekaligus untuk 20 anggota (didokumentasikan eksplisit di kode: kalau data mendekati skala NFR-02/500rb, ini WAJIB diganti pencarian & drawer server-side per-baris, bukan kirim semua ke client)
- `src/lib/sertifikasi.ts` — `computeSertifikasiStatus()` menghitung status (Aktif/Akan Kedaluwarsa/Kedaluwarsa) dari `tanggalBerlaku` setiap kali di-query, BUKAN dipercaya dari kolom `status` tersimpan — ini yang bikin FR-06 ("badge berubah warna otomatis") benar-benar valid, bukan cuma snapshot statis. Dipakai konsisten di Direktori Anggota, drawer CV, dan menu Kompetensi & Sertifikasi
- `src/lib/anggota-actions.ts` — Server Actions `createAnggotaAction`/`updateAnggotaAction`/`deactivateAnggotaAction`/`updateStatusSiagaAction`, semua: (1) cek role via `auth()` di dalam action itu sendiri (RBAC di server, bukan cuma sembunyi tombol di client — Analis yang coba manggil action tetap ditolak), (2) validasi Zod (NIK regex 16 digit), (3) tulis `AuditLog` via helper baru `src/lib/audit-log.ts`, (4) `revalidatePath` supaya UI ter-update otomatis tanpa reload manual
- Drawer CV: foto placeholder siluet, data pribadi (usia dihitung dari tanggal lahir), kompetensi (diturunkan dari daftar jenis Sertifikasi — skema tidak punya field kompetensi terpisah dari sertifikasi formal, disederhanakan secara sadar), sertifikasi, riwayat pelatihan, riwayat penugasan (join ke Misi), tombol ubah status siaga + edit + nonaktifkan (khusus Super Admin/Operator)
- **Bug nyata ditemukan & diperbaiki lewat testing Playwright** (bukan cuma "kelihatan jalan"): alur Edit → Escape → Tambah Anggota → Simpan ternyata memanggil `updateAnggotaAction` dengan id anggota LAMA, bukan `createAnggotaAction` — root cause: `AnggotaFormModal` dipakai berulang untuk create & edit dengan `action` yang berbeda tiap kali (`updateAnggotaAction.bind(null, id)` vs `createAnggotaAction`), dan komponennya tidak pernah unmount sehingga `useActionState` di dalamnya bisa membawa binding lama. Diperbaiki dengan `key={formTarget ? `edit-${id}` : "create"}` supaya React memaksa remount komponen (dan hook di dalamnya) tiap kali target berpindah. Reproduksi & fix dikonfirmasi lewat pengecekan log server (`createAnggotaAction` vs `updateAnggotaAction` yang benar-benar terpanggil), bukan cuma asumsi dari UI yang terlihat benar
- **Verifikasi lengkap**: search/filter tabel, buka drawer, ubah status siaga (server action beneran ke-invoke, dicek dari log), buka modal edit dengan data ter-isi benar, create anggota baru (row baru muncul otomatis lewat `revalidatePath`, tanpa reload), halaman Sertifikasi & Pelatihan — semua lewat browser Playwright sungguhan, nol console error di sepanjang alur

## Catatan Lingkungan Dev (penting untuk sesi lanjutan)

Mesin dev ini **tidak** punya Node.js/npm bawaan dan **tidak** ada akses admin (MSI installer Node gagal — Error 1925 insufficient privileges). Solusinya:
- Node.js v24.19.0 diinstal sebagai **portable zip** ke `%LOCALAPPDATA%\Programs\node-v24.19.0-win-x64` (bukan via installer resmi)
- Ditambahkan ke **User PATH** (registry) — berlaku untuk sesi shell baru
- Untuk Git Bash yang sesi-nya sudah berjalan sebelum PATH diubah: dibuat wrapper `node`/`npm`/`npx` (bash script) di `~/bin` — folder ini sudah ada di PATH bawaan Git Bash
- **Penting:** subprocess native Windows (cmd.exe, yang dipanggil banyak install script npm seperti Prisma postinstall) butuh file `.cmd` asli, bukan bash script. Maka dibuat juga `node.cmd`, `npm.cmd`, `npx.cmd` di `~/bin` yang memanggil `node.exe` asli dengan path absolut — tanpa ini, `npm install` gagal dengan `'node' is not recognized` setiap kali sebuah package menjalankan install script.
- Kalau lingkungan dev berubah (mesin baru / container baru), langkah instalasi Node portable + shim `.cmd` ini perlu diulang kalau tidak ada akses admin untuk installer resmi.
- npm 11+ punya fitur `allow-scripts` (block install script secara default) — kalau ada package baru yang install-nya gagal diam-diam, cek `npm approve-scripts --allow-scripts-pending` dulu.
- **`localhost` sempat tidak resolve** di dalam sesi kerja ini tapi `127.0.0.1` selalu jalan — kalau curl/browser gagal connect ke `localhost:3000`, coba `127.0.0.1:3000`.
- Git Bash + `cmd.exe /c "..."` sering memangkas argumen `/c` jadi path (MSYS path-mangling) — pakai `cmd.exe //c "..."` (garis miring ganda) kalau perlu menjalankan command lewat cmd.exe dari Git Bash.

## Keputusan Teknis yang Diambil Selama Sesi Ini

- **Prisma versi**: dipin ke `^6` (bukan v7 terbaru) karena Prisma 7 mengubah cara konfigurasi datasource (butuh `prisma.config.ts` + driver adapter, breaking change besar). v6 tetap pakai `url` di `schema.prisma` seperti biasa.
- **Tailwind v4**: dipakai apa adanya dari default `create-next-app` — theming lewat `@theme` block di CSS, bukan `tailwind.config.js`.
- **Next.js 16 "proxy" bukan "middleware"**: file route-protection ada di `src/proxy.ts`, bukan `src/middleware.ts` (nama lama dideprecate mulai Next 16.0.0).
- **Login pakai Server Action, bukan client `signIn()`**: `src/app/login/actions.ts` memanggil `signIn` dari `@/lib/auth` (server-side), ditangkap lewat `useActionState`. Ini menghindari perlu `"use client"` untuk seluruh logic auth dan `AuthError` ditangani rapi tanpa expose detail error ke user.
- **RBAC di level proxy (route), bukan cuma UI**: halaman Command Center & Sisi Anggota benar-benar saling terkunci di server (redirect), bukan cuma sembunyi-tampil elemen di client. Pola yang sama dilanjutkan di level Server Action untuk operasi CRUD (Fase 5) — jangan pernah cuma andalkan sembunyi tombol di UI untuk otorisasi.
- **lucide-react tidak lagi punya ikon brand** (Instagram, LinkedIn, dll — versi 1.31.0 yang terpasang). Kalau butuh ikon sosial media lagi di modul lain, pakai ikon generik (`AtSign`, `Link2`, dll) seperti di CV drawer, bukan asumsi nama ikon brand tersedia.
- **`key` prop untuk memaksa remount komponen form yang dipakai ulang untuk create/edit**: kalau ada component dengan `useActionState` yang di-reuse untuk beberapa "target" berbeda (create vs edit-anggota-X vs edit-anggota-Y) tanpa pernah unmount, action binding bisa nyangkut ke target lama. Di Fase 6, `BuatMisiModal` dihindarkan dari masalah ini karena selalu single global instance (bukan di-reuse per-record) dan wizard state di-reset manual saat modal ditutup — tapi kalau nanti ada form Misi yang di-reuse per-record (mis. edit Misi), ingat pola ini.
- **Server Action dipanggil langsung dari client (bukan via `useActionState`+form)** untuk alur multi-step: `generateMisiAction`/`approveMisiAction`/`closeMisiAction` dipanggil sebagai fungsi async biasa di dalam `startTransition`, bukan di-bind ke `<form action>`. Ini valid untuk fungsi `"use server"` yang diimpor ke client component, dan lebih cocok untuk wizard (form → loading → result → approve) dibanding `useActionState` yang mengasumsikan satu form dengan satu hasil.
- **Prisma destructive command (`db push --force-reset`) diblokir otomatis** oleh guard Claude Code sendiri kalau dijalankan tanpa konfirmasi user eksplisit di pesan itu — ini best-practice yang sengaja tidak dilewati (bukan di-bypass pakai flag tersembunyi). Kalau perlu reset dev DB lagi nanti, minta izin dulu ke user sebelum menjalankan `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION=... npx prisma db push --force-reset`.
- **OpenAI structured output (`response_format: json_schema` + `enum` pada field)** efektif untuk grounding: dengan meng-*enum*-kan `anggotaId` ke daftar kandidat asli yang dikirim, model API secara struktural tidak bisa mengembalikan personel di luar itu — divalidasi ulang juga di kode (`validIds.has(...)`) sebagai defense-in-depth, bukan cuma percaya skema.
- **`serverExternalPackages` di `next.config.ts`** wajib untuk paket Node yang membaca asset (font, native binding, dsb) relatif ke `__dirname`-nya sendiri saat runtime (`pdfkit` contoh nyata di Fase 7) — kalau di-bundle Turbopack/webpack, `__dirname` berubah jadi path virtual dan asset itu tidak ketemu (`ENOENT`). Cek dulu paket serupa (`canvas`, native addon apa pun) kalau muncul gejala sama di fase berikutnya.
- **Route Handler (`app/api/.../route.ts`) untuk unduhan file**: dipakai untuk laporan PDF/XLSX supaya browser bisa native-download via `Content-Disposition: attachment`. Link `<a href>` biasa (bukan `router.push`) atau `window.location.href` di client dipakai untuk memicunya — `router.push` tidak akan memicu dialog unduh karena itu navigasi client-side RSC, bukan request browser penuh.
- **`signIn(..., {redirectTo})` di Server Action jangan hardcode satu tujuan untuk semua role** — redirect dari dalam Server Action adalah client-side transition yang ternyata tidak memicu ulang `proxy.ts` secara andal di lingkungan ini (ditemukan di Fase 11). Tentukan tujuan redirect dari data sungguhan (role) SEBELUM memanggil `signIn()`, jangan berharap middleware "membenarkan" tujuan yang salah di request berikutnya.
- **Prisma: field `xxxId String?` polos BUKAN relasi** — kalau mau `include`/`select` relasi itu di query, harus eksplisit tambah `xxx Model? @relation(fields:[xxxId], references:[id])` plus array balik di model lawannya. `Notifikasi.misiId` sudah ada sejak Fase 6 tapi baru punya relasi asli di Fase 11 saat benar-benar butuh `include: {misi:true}` — sebelum itu field-nya cuma string biasa yang kebetulan berisi id valid.
- **Field terenkripsi tidak bisa `@unique` langsung** (Fase 12, NIK): kalau sebuah kolom butuh enkripsi at-rest DAN kolom itu juga jadi kunci pencarian/unik, jangan enkripsi kolom yang sama — tambah kolom hash deterministik terpisah (HMAC, bukan enkripsi acak) khusus untuk lookup/`@unique`, simpan nilai terenkripsi di kolom aslinya untuk ditampilkan lagi. Dua kolom, dua tujuan berbeda: satu bisa dibalik (untuk dilihat user berwenang), satu tidak (cuma untuk dibandingkan).
- **Client component tidak boleh value-import dari file data-fetcher Prisma**, walau cuma untuk satu fungsi murni di dalamnya — modul JS dieksekusi utuh saat diimpor, jadi `import { prisma }` di baris atas ikut jalan di bundle browser dan Prisma Client sendiri akan melempar error di sana. Ini nyaris jadi bug tersembunyi di Fase 5 dan baru pecah di Fase 12 gara-gara perubahan kecil di `prisma.ts` mengubah hasil tree-shaking bundler. Aturan aman: dari client component, HANYA `import type` dari file data-fetcher; util murni yang dipakai bersama (kayak `calcUsia`) harus tinggal di file terpisah tanpa dependensi server sama sekali.
- **Leaflet `markerPane` (Marker/divIcon) SELALU di atas `overlayPane` (CircleMarker/Circle/Polygon)** — ini z-index bawaan Leaflet (600 vs 400), bukan sesuatu yang bisa diatur lewat prop React biasa. Kalau ada dua layer data yang koordinatnya bisa berdekatan/bertabrakan (Fase 14: Pos Komando pakai Marker, anggota pakai CircleMarker), Marker akan selalu "menang" secara klik walau CircleMarker terlihat di atasnya secara visual pada zoom tertentu. Solusinya bukan CSS/z-index — jauhkan koordinatnya, atau pakai custom pane kalau memang perlu urutan berbeda.
- **CSS kustom di `globals.css` WAJIB dibungkus `@layer components`** (Fase 15). Tailwind v4 menaruh seluruh utility-nya di `@layer utilities`, dan aturan CSS TANPA layer selalu menang atas aturan BER-layer — terlepas dari specificity, dan kebalikan dari intuisi "yang belakangan menang". Kelas `.hud-brk { position: relative }` yang unlayered membajak semua elemen ber-`absolute`/`fixed` dari Tailwind: panel peta terlempar ke aliran normal dan modal Radix kehilangan posisi tengahnya. Berlaku untuk kelas kustom apa pun yang mengatur properti yang juga punya utility Tailwind (`position`, `background`, `display`, dst).
- **Updater `setState` harus murni — jangan memutasi apa pun di dalamnya** (Fase 15). React StrictMode di dev sengaja memanggil updater dua kali untuk mendeteksi ketidakmurnian, dan memakai hasil panggilan terakhir. Flag "sudah dipulihkan" yang dimutasi di dalam updater membuat panggilan kedua mengambil cabang berbeda, sehingga hasil pemulihan dari `localStorage` dibuang diam-diam. Gejalanya bukan error, cuma "nilai selalu balik ke default" — baca sumber eksternal di luar updater.
- **Screenshot harus dibandingkan ke referensi, bukan cuma dilihat** (Fase 15). Regresi tata letak panel peta lolos dari verifikasi walau screenshot-nya dibuka, karena dibaca sebagai "begini tampilannya" alih-alih dicocokkan ke mockup yang jadi acuan. Untuk perubahan yang menyentuh banyak permukaan sekaligus, daftar periksa harus diturunkan dari sifat perubahannya (mis. "semua elemen ber-`absolute`/`fixed`"), bukan dari halaman yang kebetulan teringat.
- **Overlay dekoratif yang menutupi seluruh viewport WAJIB `pointer-events: none`** (Fase 15). Tekstur global HUD (`body::before/::after`) berada di `z-index` 9998/9999, jauh di atas modal & drawer Radix (2000/2001) — tanpa `pointer-events: none`, seluruh aplikasi jadi tidak bisa diklik sama sekali dan gejalanya terlihat seperti "semua tombol rusak", bukan seperti masalah CSS. Berlaku untuk overlay dekoratif apa pun yang ditambahkan nanti.

FRD §10.2 mengunci palet, jadi Sentinel HUD dibangun murni dari utility tambahan di `globals.css` (gradien tipis, glow, tekstur, corner bracket) tanpa mengubah satu pun nilai hex. - **Untuk perubahan gaya yang polanya identik di banyak file** (Fase 15: 7 file tabel dengan string kelas yang persis sama), penggantian mekanis lewat script sekali-pakai lebih aman daripada belasan edit manual — asalkan langsung diikuti `tsc` + `lint` + screenshot verifikasi. Alasan opsi hover-reveal tidak direkomendasikan meski paling "bersih": tidak terlihat di layar sentuh dan tidak muncul di screenshot demo ke pemangku kepentingan — dua konteks yang justru paling butuh penjelasan nama.

**Regresi berat dari fase ini sendiri — dilaporkan user, bukan ketahuan dari verifikasi saya.** Seluruh kelas chrome HUD ditulis di `globals.css` **tanpa `@layer`**, sedangkan Tailwind v4 menaruh utility-nya di `@layer utilities`. Aturan CSS tanpa layer selalu menang atas aturan berlayer — terlepas dari specificity, dan ini justru kebalikan dari intuisi kebanyakan orang tentang "CSS belakangan menang". Akibatnya `.hud-brk { position: relative }` membajak setiap elemen yang juga memakai `absolute`/`fixed` dari Tailwind: panel "Aktivitas Pelatihan" terlempar ke aliran normal (muncul di kiri, menumpuk di bawah panel Layers, terpotong) dan modal Radix kehilangan posisi tengahnya.

Kenapa lolos dari verifikasi Fase 15: saya memang membuka screenshot Overview dan melihatnya, tapi membacanya sebagai "panel pelatihan di kiri" tanpa membandingkan balik ke mockup yang saya buat sendiri — padahal di mockup jelas di kanan. Modal bahkan tidak pernah difoto sama sekali. Pelajarannya bukan "kurang teliti", tapi bahwa screenshot perlu dibandingkan ke referensi, dan setiap permukaan yang tersentuh perubahan global (di sini: semua yang ber-`absolute`/`fixed`) perlu masuk daftar periksa, bukan hanya halaman yang kebetulan diingat.

Diperbaiki dengan membungkus seluruh blok chrome HUD dalam `@layer components` sehingga utility Tailwind menang seperti seharusnya. Satu efek samping ditangani sekalian: header sticky Drawer memakai `.hud-head` bersama `bg-*`; di skema berlayer, `bg-*` sekarang menang dan sheen-nya akan hilang — jadi diubah memakai gradien bg langsung. Setelah itu disapu ke seluruh 13 route Command Center + Sisi Anggota dengan pengecekan otomatis yang membandingkan utility posisi di `className` dengan `getComputedStyle().position` sesungguhnya: nol mismatch, nol overflow horizontal.

Tata letak Overview juga disamakan ke mockup terpilih: panel Aktivitas Pelatihan di kanan atas, tombol layar penuh di pojok kanan atas (sebelumnya diletakkan di kiri panel, tidak sesuai mockup).

**Tinggi panel bawah bisa digeser user.** Permintaan user: tiga panel bawah harus bisa "ditarik-tarik" naik-turun supaya proporsi peta vs panel bisa diatur sendiri. Implementasinya pegangan geser setinggi 11px di antara peta dan baris panel, dengan `cursor: row-resize` dan garis grip yang menyala saat disorot/diseret. Tarik ke atas → panel makin tinggi; tarik ke bawah → peta makin besar.

Batasnya dijaga di dua sisi: minimum 132px untuk panel, dan maksimum `tinggi shell − 220px` supaya peta tidak bisa digeser sampai hilang. Batas atas itu bukan konstanta — diikuti lewat `ResizeObserver` pada shell, jadi tetap benar saat window di-resize atau browser di-zoom. Nilainya disimpan di `localStorage` per browser, dan pegangannya bisa dioperasikan tanpa mouse (`role="separator"` + panah atas/bawah, §10.8). Saat ketiga panel disembunyikan, pegangan ikut hilang — tidak ada yang bisa diatur ukurannya di situ.

**Bug halus ditemukan saat memverifikasinya**: pemulihan tinggi dari `localStorage` mulanya saya taruh di dalam updater `setBottomHeight`, bersama flag "sudah dipulihkan" yang dimutasi di sana. Updater jadi tidak murni — dan React StrictMode yang sengaja memanggil updater dua kali membuat panggilan kedua melihat flag sudah `true`, lalu hasil pemulihannya dibuang. Gejalanya: tinggi selalu balik ke default setiap reload, tanpa error apa pun. Diperbaiki dengan membaca `localStorage` di luar updater.

**Verifikasi:** `tsc --noEmit`, `npm run lint`, dan `npm run build` bersih. Screenshot Playwright untuk login, Overview, Direktori Anggota, Analitik, Manajemen Misi, Pengaturan, drawer CV, dan Sisi Anggota mobile (viewport 430×880) — nol console error di semuanya. Header laporan PDF diverifikasi dengan mendekompresi content stream dari file hasil unduhan sungguhan (baris 1 `SIAGA`, baris 2 kepanjangan penuh) — bukan diasumsikan dari kode. ## Fase 16 — Persiapan Deployment: Vercel + Neon Postgres

User minta cara deploy dashboard ke cloud supaya bisa diakses orang lain. Sebelum menjawab, tiga platform ditawarkan lewat `AskUserQuestion` (Vercel+Neon direkomendasikan, Railway, VPS Docker sendiri) — user memilih Vercel + Neon. Ini penting dipisah dari "rilis produksi": yang diminta adalah demo publik dengan data dummy yang sudah ada, bukan onboarding data personel TNI/Komcad sungguhan. Kedua skenario ditulis eksplisit sebagai dua sub-bagian terpisah di `app/README.md` supaya tidak ada yang salah baca "sudah online" sebagai "sudah rilis resmi".

**Migrasi provider adalah keharusan teknis, bukan pilihan.** SQLite menyimpan data sebagai file di filesystem; hosting serverless (Vercel) punya filesystem yang ephemeral per-invocation, jadi `dev.db` tidak akan bertahan atau tersinkron antar-request begitu di-deploy. Ini sudah diantisipasi sejak Fase 0 (`CLAUDE.md` sejak awal menulis "dev SQLite karena mesin ini tidak ada Docker, prod ganti provider saat rilis") — Fase 16 adalah saat keputusan itu benar-benar dieksekusi. Sebelum mengganti provider, kode disapu dulu (`grep` untuk `$queryRaw`/`$executeRaw`/sintaks SQLite) — nol ditemukan, schema memang sengaja portable sejak awal (`String` bukan native enum), jadi migrasi provider murni ganti satu baris `datasource`.

**Konsekuensi yang sengaja tidak disembunyikan:** dev lokal juga ikut pindah ke Postgres, bukan tetap SQLite di lokal + Postgres di prod. Prisma tidak mendukung dua provider berbeda dalam satu file schema, dan menjaga dua schema terpisah (SQLite untuk dev, Postgres untuk prod) berarti setiap perubahan model harus ditulis dua kali dan bisa diam-diam divergen — risikonya lebih besar dari sekadar "harus pasang Postgres di lokal juga". Disarankan pakai branch/project Neon terpisah untuk dev vs demo publik, supaya `prisma db push --force-reset` yang biasa dipakai saat iterasi cepat di lokal tidak pernah menyentuh data yang sedang diakses orang lain — ini ditulis sebagai peringatan eksplisit di README, bukan diasumsikan orang akan hati-hati sendiri.

**Yang disiapkan di sisi repo:** provider `schema.prisma` → `postgresql`; `package.json` dapat `postinstall: prisma generate` (Vercel install `node_modules` fresh tiap build, dan Prisma Client hasil generate tidak ikut ter-commit ke git — tanpa ini, build Vercel akan gagal karena `@prisma/client` belum punya kode yang di-generate) plus script `db:migrate`/`db:migrate:deploy` sebagai pembeda eksplisit dev vs prod; `app/README.md` bagian Deployment ditulis ulang total jadi langkah konkret (provisioning Neon, root directory `app` di Vercel — bukan default, karena kode Next.js ada di subfolder, env var per environment, override Build Command jadi `prisma generate && prisma migrate deploy && next build` supaya migrasi jalan otomatis tiap deploy berikutnya tanpa langkah manual).

**Yang TIDAK bisa dikerjakan agent:** membuat akun Neon/Vercel, menghubungkan repo GitHub ke project Vercel, mengisi environment variable di dashboard mereka, dan menjalankan migrasi+seed pertama ke database production sungguhan — semua ini butuh akun cloud milik user. Langkah-langkah itu ditulis selengkap mungkin di README supaya user bisa jalan sendiri tanpa perlu balik bertanya di setiap langkah, tapi statusnya tetap "belum dieksekusi", bukan "sudah live", sampai user mengonfirmasi.

**Verifikasi tanpa database sungguhan (sebelum user mulai bagian akun cloud):** `npx prisma generate` cuma butuh schema valid secara sintaks, tidak butuh koneksi DB — sukses. `tsc --noEmit`, `npm run lint`, `npm run build` semuanya bersih memakai `DATABASE_URL` dev lama yang sudah tidak valid untuk provider baru — ini membuktikan `next build` tidak menyentuh database sama sekali untuk route dinamis (yang jadi mayoritas route platform ini), cuma untuk route statis (`/`, `/login`).

### Eksekusi bersama user: dari "sisi repo siap" jadi "live"

Bagian akun cloud dikerjakan user sambil dituntun agent langkah-demi-langkah secara sinkron di chat — bukan sekadar diserahkan ke README lalu ditinggal. Beberapa hal yang baru ketahuan setelah user benar-benar di UI sungguhan (bukan didokumentasikan dari ingatan/asumsi):

- **UI Neon yang dipakai user beda dari yang saya asumsikan**: branch default namanya `production` (bukan `main`), dan project baru otomatis dapat 2 branch tanpa perlu bikin manual — kebalikan dari urutan yang saya tulis duluan. Dialog "Connect" juga tidak lagi punya dropdown preset per-framework ("Prisma"/"Next.js"), cuma satu connection string generik dengan toggle pooling. User mengoreksi ini lewat screenshot, README langsung diperbaiki saat itu juga supaya sesi berikutnya tidak mewarisi instruksi yang salah.
- **`DATABASE_URL_UNPOOLED`/`directUrl` yang disarankan Neon di snippet-nya ternyata tidak relevan** — komentarnya sendiri bilang "uncomment kalau Prisma <5.10", dan repo ini Prisma 6. Dicek langsung ke `schema.prisma`: sudah pas apa adanya, nol perubahan dibutuhkan.
- **Secret sungguhan sempat masuk ke chat** (`AUTH_SECRET`/`ENCRYPTION_KEY` di-generate agent, connection string Neon ditempel user termasuk password-nya). Ini file `.env` lokal — gitignored, tidak pernah menyentuh git — dan agent langsung memakainya untuk mengisi `.env` lokal user serta menjalankan migrasi/seed, bukan sekadar menampilkan ulang secretnya di chat berulang kali.
- **Bug nyata ditemukan di tengah eksekusi**: `prisma migrate deploy` pertama ke branch `production` gagal dengan `P1002` — "timed out trying to acquire a postgres advisory lock". Root cause: branch `production` belum pernah diakses sama sekali sejak dibuat, jadi compute-nya cold-start dari nol (Neon scale-to-zero) dan proses bangunnya lebih lama dari timeout lock 10 detik. Bukan masalah schema atau konfigurasi. Retry kedua langsung sukses ("No pending migrations to apply") — tapi sebelum lanjut ke seed, dijalankan `prisma migrate status` dulu untuk memastikan attempt pertama yang gagal tidak meninggalkan tabel setengah-jadi. Hasilnya bersih: "Database schema is up to date!"
- **Verifikasi akhir bukan cuma percaya kata user** ("it worked") — agent menjalankan Playwright sungguhan ke `https://komcad-ai-dashboard.vercel.app`: login `admin@komcad.mil.id` sungguhan, sampai Overview termuat, 60 anggota di panel Statistik, peta + 3 panel bawah render, nol console error. Screenshot-nya dilihat langsung.

### Susulan Fase 16: alur staging → production

Segera setelah demo publik live, user minta perubahan jangan langsung tampil di domain publik — mau ada tahap review dulu. Dibangun murni dari fitur native Vercel (Preview Deployment per branch) + Neon (branching), tanpa tooling tambahan: branch git `staging` baru, branch Neon ketiga `staging` (di-branch dari `production`, dapat data instan lewat copy-on-write — bukan dari `main`/dev, karena dev pakai `db push` yang tidak tercatat migrasi sedangkan Preview pakai `migrate deploy` yang strict terhadap riwayat itu; kalau satu branch dipakai keduanya berisiko drift), env var `DATABASE_URL`/`AUTH_SECRET`/`ENCRYPTION_KEY` di-scope "Preview" saja di Vercel.

Satu temuan yang menghemat kerjaan: Build Command yang di-override untuk Production di awal Fase 16 ternyata **project-wide**, otomatis berlaku juga untuk Preview — tidak perlu di-override terpisah untuk staging.

Satu bug kecil: push pertama branch `staging` tidak langsung memicu Preview Deployment (webhook GitHub→Vercel kelewat) — diperbaiki dengan commit kosong untuk re-trigger.

Satu batasan verifikasi yang jujur dicatat: Vercel otomatis memasang Deployment Protection (SSO) di semua Preview deployment — bagus sesuai maksud staging (bukan publik), tapi berarti agent tidak bisa lagi verifikasi mandiri lewat curl/Playwright (kena redirect ke halaman login Vercel). Untuk bagian staging ini, laporan user diterima apa adanya — beda dari verifikasi Production yang selalu dicek ulang independen.
